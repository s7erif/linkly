# PROJECT_ANALYSIS.md

## 1. Current Architecture
- **Framework**: Next.js App Router.
- **Stack**: React, Tailwind CSS, Prisma ORM, PostgreSQL, NextAuth.
- **Data Flow**: The architecture currently relies on heavily coupled Client Components (`page.js`, `gallery/page.js`) that directly fetch from Next.js API routes, which in turn use Prisma to access the database.
- **UI/Logic Separation**: Poor. Business logic, state management, and UI rendering are tightly coupled in monolithic files, contrary to the `ARCHITECTURE.md` specification.

## 2. Current Database
- **Provider**: PostgreSQL via Prisma.
- **Models**: Includes NextAuth models (`User`, `Account`, `Session`) and `BusinessCard`.
- **Status**: Phase 2A database refactoring has partially started. AI fields were removed, and `slug` + `isActive` were added.
- **Deficiencies**: 
  - `socialLinks` are stored as stringified JSON in the `BusinessCard` table instead of a normalized `SocialLink` model.
  - `Analytics` model is completely missing.
  - `avatar` and `backgroundImage` store Base64 data URLs rather than external URLs, which bloats the database.

## 3. Current APIs
- **`/api/cards`**: Handles CRUD operations for `BusinessCard`. Lacks Zod validation (relies on manual conditional checks) and pagination.
- **`/api/upload`**: Converts uploaded files directly into Base64 data URLs and returns them. This is highly inefficient.
- **`/api/download`**: Proxy for downloading images via URL.
- **Deficiencies**: Missing APIs for analytics, social links management, themes, settings, public vCard generation, and public QR generation as defined in `API_SPEC.md`.

## 4. Current Dashboard
- **Editor (`/page.js`)**: A monolithic ~940-line Client Component managing form state, template selection, saving, and previewing.
- **Gallery (`/gallery/page.js`)**: A ~330-line Client Component listing the user's cards.
- **Deficiencies**: 
  - Violates `CODING_STANDARDS.md` (components should be < 200 lines).
  - Lacks an Overview/Statistics page.
  - Form state management is manual and complex.
  - UI components (Inputs, Buttons, Modals) are hardcoded and duplicated rather than reusable.

## 5. Current Public Pages
- **Routing**: Currently relies on `urlHash` (`/card/[hash]`) rather than the specified `slug` routing.
- **Rendering**: The public card view uses `CardVisitorView.jsx` which embeds an `iframe`. The `iframe` is populated by raw HTML strings generated by `generateCardDocument` in `lib/templates.js`.
- **Deficiencies**: The public view is completely disconnected from Next.js React components, making it difficult to maintain, optimize, and extend.

## 6. Current Components
- **Existing**: Only `Navbar.js` and `Footer.js` exist in `src/components/`.
- **Missing**: The `UI_SPEC.md` and `CODING_STANDARDS.md` mandate a reusable UI library (e.g., Button, Card, Dialog, Avatar, QR, Section), but none have been implemented. Composition is entirely bypassed in favor of inline HTML/Tailwind.

## 7. Technical Debt
- **HTML Template Generation**: `src/lib/templates.js` is a ~54KB file generating raw HTML strings for themes. This violates the `THEMES_SPEC.md` requirement that themes use React components.
- **Monolithic Files**: `src/app/page.js` and `src/app/gallery/page.js` need immediate refactoring into smaller components.
- **Base64 Image Storage**: Storing images as Base64 strings in the database severely limits scalability and hurts performance.
- **Validation**: Missing strict runtime validation (e.g., Zod) on API boundaries.
- **JSON Storage**: Relational data (Social Links) stored as stringified JSON.

## 8. Missing Features
- **Database Models**: `SocialLink`, `Analytics`.
- **Dashboard Sections**: Overview/Stats, Company Settings, Theme Management.
- **Public Card**: vCard (`.vcf`) generation endpoint, Analytics tracking (Views, QR Scans, Clicks), `slug`-based routing.
- **Theming**: Configurable Brand Colors, Theme Variants (Dark/Light).

## 9. Security Concerns
- **Data Validation**: API routes trust client payloads without comprehensive validation schemas.
- **Base64 Uploads**: The `/api/upload` route accepts files and converts them to Base64 in memory. Without strict size limits and proper external storage, this can easily lead to memory exhaustion and database bloat (Denial of Service risk).
- **Authorization**: While `session?.user` is checked, ensuring users can only edit their own nested resources (once `SocialLink` is added) must be strictly enforced.

## 10. Performance Concerns
- **Base64 Images**: Serving 5MB base64 strings within database queries will massively degrade database response times and API payload sizes.
- **Iframe Overhead**: The use of an `iframe` for rendering templates adds unnecessary DOM overhead and restricts React's hydration benefits on public pages.
- **Missing Pagination**: The `GET /api/cards` route fetches all cards at once, which will fail to scale as user accounts grow.

## 11. Refactoring Opportunities
- **Extract UI Library**: Build a foundational set of atomic React components in `src/components` (e.g., `Input`, `Button`, `Modal`).
- **Dashboard Modularization**: Break `page.js` into `CardEditor`, `CardPreview`, and `SharePanel` components. Use a state management solution or proper React Context for form data.
- **Themes to React Components**: Replace `lib/templates.js` with individual React components in a `src/components/themes/` directory as specified by `THEMES_SPEC.md`.
- **Cloud Storage**: Replace Base64 conversions with a cloud object storage provider (e.g., AWS S3, Vercel Blob) for avatars and cover images.

## 12. Recommended Implementation Order
1. **Phase 2 (Database Refactor)**: Normalize `SocialLink`, add `Analytics` models, and implement strict Zod validation on APIs. Implement cloud storage to replace Base64 images.
2. **Phase 3 (Dashboard Refactor)**: Create reusable UI components. Refactor `page.js` and `gallery.js` into modular components. Add the Overview dashboard.
3. **Phase 4 & 5 (Public Card & Themes)**: Rewrite templates as React Server/Client Components. Implement `slug`-based public routing and vCard generation.
4. **Phase 6 (Analytics)**: Implement tracking logic for page views, clicks, and QR scans.
5. **Phase 7 & 8 (Branding & Testing)**: Finalize company settings, brand colors, and comprehensively test performance and accessibility.
